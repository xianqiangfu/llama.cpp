# 多设备协同问题总结

## 概述

多设备协同（多 GPU、多 NPU 等）是 llama.cpp 的重要功能，能够扩展显存容量和提高推理吞吐量。然而，多设备环境下的协同工作涉及复杂的设备间通信、负载均衡、同步机制等问题，可能引发性能瓶颈、稳定性问题和精度损失。本文档总结了多设备协同的常见问题、原因分析和解决方案。

## 常见多设备协同问题

### 1. 设备发现和枚举问题

**问题描述：**
llama.cpp 无法正确识别或使用所有可用设备，导致资源利用不充分。

**常见症状：**
- 部分设备未被检测到
- 设备 ID 分配错误
- 设备能力识别不准确

**原因分析：**
1. **驱动和后端问题**
   - 驱动版本不兼容
   - 后端初始化失败
   - 环境变量设置错误

2. **设备权限问题**
   - 用户缺少设备访问权限
   - 设备组配置不当
   - 安全策略限制

3. **硬件配置问题**
   - PCIe 带宽限制
   - 设备连接不稳定
   - 电源管理影响

**解决方案：**

```bash
# 列出所有可用设备
./llama-cli --list-devices

# 检查 CUDA 设备
nvidia-smi
export CUDA_VISIBLE_DEVICES=0,1,2,3

# 检查 SYCL 设备
sycl-ls
export ONEAPI_DEVICE_SELECTOR="level_zero:0;level_zero:1"

# 检查用户权限
sudo usermod -aG video $USER
sudo usermod -aG render $USER
```

### 2. 内存分配和管理问题

**问题描述：**
多设备环境下，内存分配不当导致 OOM（内存不足）或性能下降。

**常见问题：**

1. **显存分配不均**
   - 某些设备显存占用过高
   - 内存碎片化
   - 分配失败导致回退到 CPU

2. **KV 缓存管理**
   - KV 缓存在设备间分布不当
   - 缓存同步开销过大
   - 缓存类型不兼容

3. **跨设备内存传输**
   - 频繁的设备间数据传输
   - 传输路径非最优
   - 带宽成为瓶颈

**解决方案：**

```bash
# 手动设置分配比例
./llama-cli -m model.gguf --tensor-split 3,1  # GPU0:75%, GPU1:25%

# 调整 KV 缓存类型
./llama-cli -m model.gguf --cache-type-k f16 --cache-type-v f16

# 限制上下文大小
./llama-cli -m model.gguf -c 4096  # 减少内存使用

# 启用自动适配（非 tensor 模式）
./llama-cli -m model.gguf --fit on
```

### 3. 分割模式选择问题

**问题描述：**
不同的分割模式（layer vs tensor）在性能和适用场景上差异显著，选择不当可能导致性能下降。

**分割模式对比：**

| 模式 | 描述 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| `none` | 单设备模式 | 简单稳定 | 无法利用多设备 | 显存足够，简单场景 |
| `layer` | 流水线并行 | 兼容性好，预填快 | 生成时延迟高 | 大模型，慢速互联 |
| `tensor` | 张量并行 | 生成时延迟低 | 互联敏感，实验性 | 快速互联，低延迟需求 |
| `row` | 行分割（已弃用） | - | 性能差 | 避免使用 |

**选择建议：**

1. **流水线并行（layer 模式）**
```bash
# 适用于大多数场景
./llama-cli -m model.gguf --split-mode layer

# 自定义分割比例
./llama-cli -m model.gguf --split-mode layer --tensor-split 2,1
```

2. **张量并行（tensor 模式）**
```bash
# 实验性功能，需要特定条件
./llama-cli -m model.gguf --split-mode tensor \
  --flash-attn on \
  --cache-type-k f16 \
  --cache-type-v f16

# 注意：不支持 KV 缓存量化和某些模型架构
```

### 4. 设备间通信瓶颈

**问题描述：**
设备间通信成为性能瓶颈，导致多设备性能低于预期。

**通信问题类型：**

1. **PCIe 带宽限制**
   - PCIe 版本和通道数不足
   - 跨 NUMA 节点通信
   - 总线竞争和拥塞

2. **同步开销**
   - 频繁的设备间同步
   - 同步原语效率低
   - 等待时间过长

3. **数据传输效率**
   - 传输粒度不当
   - 未利用高效传输机制
   - 重复数据传输

**优化方案：**

```bash
# 启用 CUDA P2P（如果支持）
GGML_CUDA_P2P=1 ./llama-cli -m model.gguf --split-mode tensor

# 使用 NCCL 优化通信
cmake -DGGML_CUDA_NCCL=ON ..  # 编译时启用

# 选择合适的分割模式
# 慢速互联：使用 layer 模式
./llama-cli -m model.gguf --split-mode layer

# 快速互联（如 NVLink）：使用 tensor 模式
./llama-cli -m model.gguf --split-mode tensor
```

### 5. 负载均衡问题

**问题描述：**
设备间负载不均导致某些设备过载而其他设备闲置，整体性能下降。

**负载不均原因：**

1. **静态分配不当**
   - 预估的设备能力不准确
   - 固定分配比例不适应实际负载
   - 忽略设备性能差异

2. **动态负载变化**
   - 不同推理阶段的负载差异
   - 批处理大小变化
   - 模型架构特性影响

3. **异构设备环境**
   - 不同型号/代际的 GPU
   - 性能差异显著的设备组合
   - 不同后端的设备混合

**解决方案：**

```bash
# 手动调整负载分配
./llama-cli -m model.gguf --tensor-split 4,2,1  # GPU0:57%, GPU1:29%, GPU2:14%

# 选择主设备
./llama-cli -m model.gguf --main-gpu 0

# 监控设备利用率
watch -n 1 nvidia-smi

# 针对异构设备优化
# 更快的设备分配更多层
./llama-cli -m model.gguf --tensor-split 3,1,1
```

### 6. 模型架构兼容性问题

**问题描述：**
某些模型架构不支持特定的多设备分割模式，导致运行失败或性能下降。

**不支持的架构：**

1. **张量并行不支持**
   - MoE/混合架构：Grok, MPT, OLMoE, DeepSeek2 等
   - 状态空间模型：Mamba, Mamba2 等
   - 特殊架构：BitNet, T5, Gemma-3n 等

2. **流水线并行限制**
   - 某些层无法独立分割
   - 跨层依赖复杂
   - KV 缓存分布限制

**解决方案：**

```bash
# 检查模型兼容性
./llama-cli -m model.gguf --split-mode tensor
# 如果出现错误，尝试 layer 模式

# 使用兼容的分割模式
./llama-cli -m model.gguf --split-mode layer

# 对于不支持多设备的架构，使用单设备
./llama-cli -m model.gguf --split-mode none --main-gpu 0
```

### 7. 性能稳定性问题

**问题描述：**
多设备环境下性能不稳定，出现波动或突然下降。

**稳定性问题类型：**

1. **热节流**
   - GPU 温度过高导致降频
   - 散热系统不足
   - 电源供应不稳定

2. **资源竞争**
   - 多个进程共享设备
   - 系统后台任务干扰
   - 网络和磁盘 I/O 竞争

3. **驱动和系统问题**
   - 驱动版本不稳定
   - 系统更新导致兼容性问题
   - 内核调度问题

**解决方案：**

```bash
# 监控温度和频率
watch -n 1 nvidia-smi

# 设置性能模式
sudo nvidia-smi -pm 1  # 持久化模式
sudo nvidia-smi -pl 300  # 功率限制

# 优化系统资源
# 限制其他 GPU 进程
# 关闭不必要的后台任务

# 使用稳定的驱动版本
# 避免使用最新的 beta 驱动
```

### 8. 调试和监控困难

**问题描述：**
多设备环境下的调试和监控复杂，问题定位困难。

**调试挑战：**

1. **日志信息不足**
   - 设备间通信细节缺失
   - 性能数据不完整
   - 错误信息不明确

2. **性能分析复杂**
   - 多维度性能指标
   - 设备间交互难以追踪
   - 瓶颈定位困难

3. **工具支持有限**
   - 标准工具不适应多设备场景
   - 可视化工具不足
   - 实时监控困难

**调试方案：**

```bash
# 启用详细日志
./llama-cli -m model.gguf --verbose --log-file debug.log

# 使用性能分析工具
nvprof ./llama-cli -m model.gguf -p "test"
nsight sys ./llama-cli -m model.gguf -p "test"

# 监控设备状态
nvidia-smi dmon -s u
nvidia-smi pmon -c 100

# 自定义脚本监控
#!/bin/bash
while true; do
    nvidia-smi --query-gpu=utilization.gpu,memory.used,memory.total --format=csv
    sleep 1
done
```

## 分割模式详细分析

### 流水线并行（Layer 模式）

**工作原理：**
- 每个设备负责连续的层切片
- KV 缓存驻留在拥有对应层的设备上
- 令牌顺序通过流水线处理

**性能特征：**
- **优点：**
  - 兼容性好，支持大多数模型
  - 设备间通信少
  - 对慢速互联容忍度高
  - 预填（prefill）性能好

- **缺点：**
  - 生成（generation）延迟高
  - 设备利用率不均
  - 需要大量令牌才能良好扩展

**适用场景：**
- 大模型需要扩展显存
- 慢速设备间互联（如 PCIe）
- 优先考虑预填性能
- 批处理场景

**配置示例：**
```bash
# 基本配置
./llama-cli -m model.gguf --split-mode layer

# 自定义分割
./llama-cli -m model.gguf --split-mode layer --tensor-split 3,2,1

# 服务器模式
./llama-server -m model.gguf --split-mode layer --parallel 4
```

### 张量并行（Tensor 模式）

**工作原理：**
- 通过"元设备"抽象分割权重和 KV
- 每层在参与设备间分割
- 每层执行多次跨设备归约

**性能特征：**
- **优点：**
  - 生成延迟低
  - 设备利用率高
  - 支持任意工作负载并行化
  - 对快速互联效果好

- **缺点：**
  - 设备间通信频繁
  - 对互联速度敏感
  - 实验性功能，成熟度较低
  - 功能限制多

**适用场景：**
- 低延迟要求的应用
- 快速设备间互联（如 NVLink）
- 实时交互场景
- 单用户场景

**配置示例：**
```bash
# 基本配置
./llama-cli -m model.gguf --split-mode tensor \
  --flash-attn on \
  --cache-type-k f16 \
  --cache-type-v f16

# 服务器模式（禁用自动适配）
./llama-server -m model.gguf --split-mode tensor \
  --flash-attn on \
  --fit off \
  --ctx-size 4096
```

**限制和注意事项：**
1. 必须启用 Flash Attention
2. KV 缓存必须使用非量化类型（f16/bf16/f32）
3. 不支持 MoE 和某些特殊架构
4. 自动适配功能被禁用
5. 代码成熟度较低，需充分测试

## 不同后端的多设备支持

### CUDA 后端

**支持特性：**
- 完整的多设备支持
- NCCL 加速通信
- P2P 访问支持
- Flash Attention 优化

**配置建议：**
```bash
# 启用 NCCL（编译时）
cmake -DGGML_CUDA_NCCL=ON ..
cmake --build . --config Release

# 运行时配置
export CUDA_VISIBLE_DEVICES=0,1,2,3
GGML_CUDA_P2P=1 ./llama-cli -m model.gguf --split-mode tensor
```

**已知问题：**
- 需要手动安装 NCCL
- P2P 可能导致不稳定
- 某些驱动版本兼容性问题

### SYCL 后端

**支持特性：**
- 多 Intel GPU 支持
- Level Zero API 优化
- 自动设备检测

**配置建议：**
```bash
# 设置设备选择
export ONEAPI_DEVICE_SELECTOR="level_zero:0;level_zero:1"

# 启用系统监控
export ZES_ENABLE_SYSMAN=1

# 运行推理
./build/bin/llama-cli -m model.gguf --split-mode layer
```

**已知问题：**
- 不支持 row 分割模式
- 性能取决于设备互联速度
- 某些功能仍在开发中

### CANN 后端

**支持特性：**
- 多 NPU 支持
- 层级分割模式
- 设备内存优化

**配置建议：**
```bash
# 单设备
./build/bin/llama-cli -m model.gguf --split-mode none --main-gpu 0

# 多设备
./build/bin/llama-cli -m model.gguf --split-mode layer
```

**已知问题：**
- 仅支持基本分割模式
- 功能受限
- 性能优化有限

## 性能优化最佳实践

### 1. 设备选择和配置

**建议：**
- 使用相同型号和代际的设备
- 确保设备间互联带宽充足
- 验证驱动版本兼容性
- 配置合适的内存分配比例

### 2. 分割模式优化

**选择原则：**
- 慢速互联 → 流水线并行
- 快速互联 → 张量并行
- 混合场景 → 测试两种模式
- 不确定 → 使用默认的 layer 模式

### 3. 内存管理优化

**策略：**
- 合理设置上下文大小
- 选择适当的 KV 缓存类型
- 启用自动适配（如果支持）
- 监控内存使用情况

### 4. 通信优化

**方法：**
- 启用 NCCL/RCCL 加速
- 使用 P2P 访问（如果稳定）
- 选择合适的分割比例
- 减少不必要的设备间传输

### 5. 负载均衡

**策略：**
- 根据设备性能分配负载
- 监控设备利用率
- 动态调整分配比例
- 避免设备空闲或过载

## 故障排查指南

### 常见错误和解决方案

**错误 1：设备未被发现**
```
error: no devices found
```
**解决方案：**
- 检查驱动安装
- 验证设备权限
- 检查环境变量
- 使用 `--list-devices` 诊断

**错误 2：内存不足**
```
error: out of memory
```
**解决方案：**
- 减少上下文大小
- 降低 KV 缓存精度
- 调整分割比例
- 减少 GPU 层数

**错误 3：张量并行失败**
```
error: SPLIT_MODE_TENSOR requires flash_attn
```
**解决方案：**
- 启用 `--flash-attn on`
- 检查模型架构兼容性
- 使用非量化 KV 缓存
- 回退到 layer 模式

**错误 4：性能低于预期**
```
performance worse than single GPU
```
**解决方案：**
- 检查 NCCL 是否启用
- 验证设备互联速度
- 尝试不同的分割模式
- 监控设备利用率

## 结论

多设备协同是扩展 llama.cpp 能力的重要手段，但需要仔细规划和配置。通过理解不同分割模式的特性、选择合适的设备和配置、持续监控和优化，可以在多设备环境中获得显著的性能提升。

关键要点：
1. 根据场景选择合适的分割模式
2. 确保设备配置和互联满足需求
3. 持续监控性能和资源使用
4. 建立故障排查流程
5. 保持系统和驱动更新

随着 llama.cpp 的发展，多设备支持将不断完善，但了解这些基础问题对于成功部署至关重要。
